# 动态游戏世界中的 LLM NPC 对话系统架构指导文档

## 1. 文档目标

本文档描述一种适用于动态游戏世界的 LLM NPC 对话系统架构。

该架构面向以下类型的游戏：

* 沙盒模拟游戏
* 涌现叙事游戏
* 开放世界 RPG
* 生存建造游戏
* 策略经营游戏
* 具备复杂 NPC 状态、事件、关系和玩家行为反馈的游戏

本文不讨论某个具体游戏或具体 mod 的实现，而是提供一种通用方法论：如何让 LLM 在不断变化的游戏世界中生成观感合适、逻辑稳定、可控且可测试的 NPC 台词。

核心观点是：

> LLM 不应该直接面对原始游戏状态并自由生成台词。
> 系统应先将游戏状态编译为结构化叙事语义，再让 LLM 在严格约束下完成语言表达。

---

## 2. 问题定义

在传统影视或线性游戏中，角色台词通常由编剧提前设计。某一时刻某个角色说出某句话，不仅依赖过去发生了什么，也依赖未来剧情将如何发展。

但在动态游戏中，未来并不固定。玩家行为、系统模拟、随机事件和 NPC 状态都会持续变化。因此，不能期待 LLM 像传统编剧一样，仅凭当前上下文就稳定生成具备长期叙事价值的台词。

一个常见但危险的方案是：

```text
游戏世界状态
  ↓
动态拼接 prompt
  ↓
LLM 生成 NPC 台词
```

这种方案早期效果明显，但随着系统复杂度上升，会出现严重问题：

* prompt 越来越长
* 上下文注入规则越来越复杂
* 玩家需要手动维护大量设定
* 护栏和兜底逻辑不断膨胀
* LLM 容易泄露角色不该知道的信息
* NPC 容易创造不存在的事实
* 对话难以稳定影响长期关系和剧情状态
* 系统很难测试、回放和调试

因此，真正的问题不是“如何把更多世界信息喂给 LLM”，而是：

> 如何在 LLM 生成台词之前，先用可测试、可审计的方式，将底层游戏状态转译为高级叙事语义。

---

## 3. 核心架构原则

### 3.1 LLM 是语言渲染器，不是游戏状态解释器

LLM 最擅长的是自然语言表达，而不是稳定解释复杂游戏状态。

它可以负责：

* 将意图写成符合角色口吻的台词
* 调整语气、节奏和风格
* 生成自然、含蓄、有人味的表达
* 在多个候选表达中提供语言变化

它不应该负责：

* 判断 NPC 是否知道某个事实
* 判断任务是否完成
* 判断行动是否合法
* 判断秘密是否可以揭露
* 判断关系数值是否应改变
* 决定是否触发实际游戏行为
* 创造未经系统确认的新世界事实

### 3.2 系统先决定“这句话为什么被说”，LLM 再决定“这句话怎么说”

每一句 NPC 台词都应该先有明确的话语功能。

例如：

```text
抱怨
试探
安慰
威胁
回避
隐瞒
求助
示好
转移话题
暴露矛盾
释放线索
拒绝承诺
请求确认
```

LLM 不应自由决定 NPC 此刻要做什么。
它应该根据系统给出的 `speech_act` 完成表达。

### 3.3 知识边界必须在 prompt 之前完成

如果某个 NPC 不知道某个事实，那么这个事实不应该进入该 NPC 的台词生成上下文。

不要把隐藏真相放进 prompt，然后告诉 LLM “不要说出来”。
正确做法是：

```text
系统真相层可以知道
导演层可以知道
校验层可以知道
角色表达层不能知道
```

角色生成层只应看到该 NPC 合法可感知、可推断、可谈论的信息。

### 3.4 记忆不是聊天记录，而是叙事账本

保存原始对话历史是不够的。

系统需要记录：

* 谁欠了谁人情
* 谁开始怀疑谁
* 哪些承诺尚未兑现
* 哪些冲突尚未解决
* 哪些秘密已经被部分揭露
* 哪些关系正在升温或恶化
* 哪些事件已经改变了 NPC 的长期态度

这类信息比完整聊天记录更重要。

### 3.5 玩家开放的是创作接口，不是底层协议

系统可以开放：

* 角色设定
* 说话风格
* 世界观
* 派系关系
* 剧情目标
* 情绪倾向
* 事件重要性
* 台词样例
* 叙事节奏偏好

但不应默认开放：

* 核心系统 prompt
* 权限过滤规则
* 知识边界规则
* 行动合法性规则
* 记忆写入规则
* 状态事务规则

否则系统稳定性会被用户 prompt、preset 或 mod 配置破坏。

---

## 4. 推荐总体架构

推荐架构如下：

```text
游戏模拟系统
  ↓
状态快照层
  ↓
事件标准化层
  ↓
主体感知与知识过滤层
  ↓
语义编译层
  ↓
叙事过程识别层
  ↓
话语行动规划层
  ↓
权限与揭露控制层
  ↓
LLM 台词渲染层
  ↓
一致性校验层
  ↓
输出层
  ↓
记忆 / 关系 / 叙事账本更新层
```

更具体地说：

```text
Raw Game State
  ↓
Game Snapshot
  ↓
Canonical Events
  ↓
NPC Knowledge Model
  ↓
Narrative Semantic Packet
  ↓
Speech Act Plan
  ↓
Prompt Render
  ↓
LLM Dialogue
  ↓
Validation
  ↓
Dialogue Output
  ↓
Ledger Update
```

---

## 5. 核心模块说明

## 5.1 状态快照层

状态快照层负责从游戏系统中读取当前世界状态。

输入可以包括：

* NPC 数值状态
* 当前地点
* 当前行为
* 最近事件
* 玩家输入
* 任务状态
* 派系状态
* 环境状态
* 战斗状态
* 物品状态
* 关系状态
* 长期记忆
* 剧情阶段

但这一层不应该直接生成 prompt。

它的职责是产生可供后续系统处理的结构化快照。

示例：

```json
{
  "npc_id": "npc_1024",
  "location": "market_square",
  "current_activity": "repairing_gate",
  "mood": -18,
  "health": {
    "injured": true,
    "fatigue": 0.72
  },
  "recent_events": [
    "attacked_by_bandits",
    "player_refused_help",
    "friend_wounded"
  ],
  "relationships": {
    "player": {
      "trust": 32,
      "fear": 18,
      "resentment": 44
    }
  }
}
```

---

## 5.2 事件标准化层

游戏内部事件通常是系统事件、数值变化或日志。
它们需要被标准化为统一格式。

例如：

```json
{
  "event_id": "event_7781",
  "type": "ally_injured",
  "subject": "npc_2048",
  "witnesses": ["npc_1024", "npc_3092"],
  "location": "north_gate",
  "time": "day_42_18:30",
  "severity": 0.76,
  "causes": ["bandit_attack"],
  "confirmed_facts": [
    "npc_2048 was injured",
    "bandits attacked the north gate"
  ]
}
```

事件标准化的目标是让后续系统能判断：

* 事件是否真实发生
* 谁亲历了事件
* 谁只是听说
* 事件严重度如何
* 事件与哪些关系、任务、地点相关
* 事件是否应进入长期记忆
* 事件是否可能改变叙事过程

---

## 5.3 主体感知与知识过滤层

这是系统中最重要的安全边界之一。

同一个世界事实，对不同主体的可见性不同。

信息应至少分为以下几类：

| 信息类型     | 说明               |
| -------- | ---------------- |
| 系统事实     | 游戏真实状态，只有系统权威层知道 |
| 作者知识     | 用于叙事控制，但角色不一定知道  |
| NPC 已知事实 | NPC 可以直接谈论       |
| NPC 感知事实 | NPC 观察到但未必理解     |
| NPC 推断   | NPC 可以根据已有信息合理猜测 |
| 玩家已知事实   | 玩家已经看到或听到        |
| 禁止泄露事实   | 当前阶段不能进入角色表达层    |
| 校验专用事实   | 只用于检查输出，不用于生成    |

错误做法：

```text
把所有事实都放进 prompt，然后要求 LLM 不要乱说。
```

正确做法：

```text
先过滤，再生成。
```

生成某个 NPC 台词时，LLM 只能看到该 NPC 的合法知识包。

---

## 5.4 语义编译层

语义编译层是整个系统的核心。

它负责将底层数值和事件转译为高级叙事语义。

它不只是总结“发生了什么”，而是判断：

* 这件事对该 NPC 意味着什么
* NPC 将责任归因于谁
* 哪些情绪正在形成
* 哪些关系正在变化
* 哪些冲突处于未完成状态
* 当前事件属于哪个长期过程
* NPC 此刻最自然的表达倾向是什么

示例输入：

```json
{
  "mood": -18,
  "recent_events": [
    "slept_in_cold_room",
    "saw_friend_wounded",
    "player_refused_help"
  ],
  "traits": ["loyal", "proud"],
  "relationship_with_player": {
    "trust": 32,
    "resentment": 44
  }
}
```

示例输出：

```json
{
  "emotional_state": {
    "primary": "resentment",
    "secondary": "exhaustion",
    "intensity": 0.68
  },
  "causal_attribution": [
    {
      "cause": "player_refused_help",
      "target": "player",
      "weight": 0.62
    },
    {
      "cause": "unsafe_living_conditions",
      "target": "colony_leadership",
      "weight": 0.51
    }
  ],
  "current_intent": "express_dissatisfaction_without_open_conflict",
  "narrative_process": {
    "arc": "trust_erosion",
    "stage": "early_warning",
    "risk": "future_confrontation"
  }
}
```

这一步最好尽量程序化。
如果早期开发成本过高，也可以使用 LLM 作为预处理 agent，但它只能输出候选语义，不能成为权威裁判。

---

## 5.5 叙事过程识别层

单个事件通常不够构成叙事。
真正有意义的是事件之间形成的过程。

例如：

```text
第一天：食物短缺
第二天：NPC 被迫加班
第三天：朋友受伤
第四天：玩家拒绝帮助
```

这些事件单独看只是状态变化。
合起来可能代表：

```text
该 NPC 正在形成“领导者不值得信任”的长期判断。
```

叙事过程识别层应识别：

* 信任腐蚀
* 关系升温
* 阵营疏离
* 创伤积累
* 复仇倾向
* 忠诚考验
* 秘密暴露
* 群体恐慌
* 生存压力
* 权力斗争
* 道德妥协
* 共同经历后的亲近

示例：

```json
{
  "process_id": "trust_erosion_player_npc1024",
  "participants": ["player", "npc_1024"],
  "stage": "early_warning",
  "evidence": [
    "player_refused_help",
    "npc_slept_in_cold_room",
    "friend_wounded"
  ],
  "current_pressure": 0.64,
  "recommended_speech_acts": [
    "bitter_complaint",
    "indirect_accusation",
    "request_reassurance"
  ],
  "forbidden_speech_acts": [
    "sudden_betrayal",
    "complete_forgiveness",
    "romantic_confession"
  ]
}
```

---

## 5.6 话语行动规划层

话语行动规划层决定 NPC 本轮发言的功能。

它回答的问题不是：

```text
NPC 要说什么？
```

而是：

```text
NPC 这句话要做什么？
```

常见话语行动包括：

| 类型                 | 作用       |
| ------------------ | -------- |
| idle_banter        | 闲聊，增强生活感 |
| complaint          | 抱怨，释放压力  |
| bitter_complaint   | 克制但带刺的抱怨 |
| ask_for_help       | 求助       |
| warn               | 警告       |
| reassure           | 安抚       |
| evade              | 回避问题     |
| conceal            | 隐瞒信息     |
| probe              | 试探       |
| accuse             | 指责       |
| threaten           | 威胁       |
| flirt              | 示好或调情    |
| apologize          | 道歉       |
| thank              | 感谢       |
| reveal_clue        | 释放线索     |
| misdirect          | 误导       |
| refuse             | 拒绝       |
| request_commitment | 要求承诺     |
| deescalate         | 降低冲突     |
| escalate           | 升高冲突     |

话语行动应由系统选择，而不是由 LLM 自由决定。

示例：

```json
{
  "speech_act": "bitter_complaint",
  "intent": "express_dissatisfaction_without_direct_rebellion",
  "target": "player",
  "intensity": 0.55,
  "allowed_topics": [
    "exhaustion",
    "unsafe_conditions",
    "feeling_ignored"
  ],
  "forbidden_topics": [
    "leaving_the_group",
    "attacking_player",
    "inventing_new_events"
  ]
}
```

---

## 5.7 权限与揭露控制层

该层决定信息能否进入台词生成上下文，以及台词是否允许触及某些内容。

信息不应只有“可见 / 不可见”两种状态。
推荐使用多级权限：

| 权限等级           | 含义             |
| -------------- | -------------- |
| speakable      | NPC 可以直接说      |
| hintable       | NPC 可以暗示，但不能明说 |
| tone_only      | 只能影响语气，不能被谈论   |
| planner_only   | 只供话语规划使用       |
| validator_only | 只供校验使用         |
| hidden         | 不进入本轮流程        |

例如：

```json
{
  "fact": "the_king_is_dying",
  "permission": {
    "npc_1024": "hintable",
    "npc_2048": "hidden",
    "narrative_director": "planner_only",
    "validator": "validator_only"
  }
}
```

这比在 prompt 中写“不要泄露国王快死了”更可靠。

---

## 5.8 LLM 台词渲染层

到这一步，LLM 才真正参与生成。

LLM 的输入不应是完整游戏状态，而应是经过处理的语义包。

示例输入：

```json
{
  "npc_voice": {
    "style": "short, restrained, dry humor",
    "formality": "low",
    "emotional_expressiveness": "controlled"
  },
  "emotional_state": {
    "primary": "resentment",
    "secondary": "exhaustion",
    "intensity": 0.68
  },
  "speech_act": "bitter_complaint",
  "intent": "express_dissatisfaction_without_open_conflict",
  "allowed_topics": [
    "tiredness",
    "unsafe work",
    "feeling ignored"
  ],
  "forbidden_topics": [
    "rebellion",
    "leaving the group",
    "inventing new incidents"
  ],
  "output_constraints": {
    "max_sentences": 2,
    "no_inner_monologue": true,
    "no_new_world_facts": true
  }
}
```

示例输出：

```text
“又是我去补那道破门。真不错，至少这次它塌下来之前，我还有机会看清是谁把我们派过去的。”
```

LLM 的职责是语言表达。
它不应决定事实、状态或行动结果。

---

## 5.9 一致性校验层

LLM 输出后，系统需要进行校验。

校验内容包括：

* 是否创造了不存在的事实
* 是否泄露了禁止信息
* 是否违背 NPC 知识边界
* 是否违背当前话语行动
* 是否语气强度过高或过低
* 是否错误承诺未来行动
* 是否把愿望说成既成事实
* 是否包含非法 action
* 是否与当前游戏规则冲突

校验可以分为两类：

### 程序化校验

适合检查：

* 禁止词
* 事实引用
* 结构格式
* action 标签
* 知识权限
* 输出长度
* 是否包含未授权实体

### LLM 辅助校验

适合检查：

* 语气是否符合要求
* 是否过度解释
* 是否太戏剧化
* 是否像该角色
* 是否偏离 speech_act

但 LLM 校验不应替代程序化权限系统。

---

## 5.10 记忆、关系与叙事账本更新层

台词输出后，系统不应只保存文本。
它应更新结构化账本。

示例：

```json
{
  "dialogue_event": {
    "speaker": "npc_1024",
    "target": "player",
    "speech_act": "bitter_complaint",
    "topics": ["unsafe_work", "feeling_ignored"],
    "intensity": 0.55
  },
  "relationship_delta": {
    "trust": -1,
    "resentment": 2
  },
  "ledger_updates": [
    {
      "type": "unresolved_grievance",
      "description": "npc_1024 expressed dissatisfaction about unsafe work",
      "participants": ["npc_1024", "player"],
      "status": "active"
    }
  ],
  "memory_write": {
    "importance": 0.46,
    "decay": "medium",
    "retrieval_tags": ["unsafe_work", "resentment", "player_leadership"]
  }
}
```

记忆系统应区分：

* 短期对话上下文
* 中期事件记忆
* 长期关系账本
* 叙事债务
* 世界事实
* 玩家承诺
* NPC 个人解释

---

## 6. 行动触发设计

NPC 台词可能涉及实际游戏行为。
例如：

```text
“我愿意加入你们。”
“我今晚会去找他。”
“我把钥匙给你。”
“我不会再帮你了。”
```

这些不能直接等同于游戏状态变化。

应设计独立的 Action Gateway。

```text
LLM 输出
  ↓
检测潜在 action intent
  ↓
程序化规则校验
  ↓
玩家确认或系统确认
  ↓
执行游戏状态变更
  ↓
写入账本
```

示例：

```json
{
  "detected_action_intent": "join_faction",
  "spoken_as_fact": false,
  "requires_validation": true,
  "validation_rules": [
    "npc_is_recruitable",
    "relationship_threshold_met",
    "not_in_combat",
    "faction_allows_recruitment",
    "player_confirmation_required"
  ]
}
```

原则：

> NPC 可以表达愿望，但不能凭一句台词直接改写游戏状态。

---

## 7. 双 Agent 方案

在早期开发中，可以使用两个 agent 降低工程成本。

```text
游戏状态
  ↓
权限过滤，程序化
  ↓
预处理 Agent
  ↓
结构化语义包
  ↓
台词生成 Agent
  ↓
校验器
  ↓
输出
```

其中：

### 预处理 Agent

负责输出候选语义：

* 当前情绪
* 归因对象
* 叙事过程
* 推荐话语行动
* 可谈话题
* 禁止话题
* 风格建议

但它不能决定：

* 事实是否成立
* NPC 是否知道某事
* 行动是否执行
* 关系是否真正改变
* 秘密是否正式揭露

### 台词生成 Agent

负责将语义包渲染为自然语言。

双 Agent 方案适合：

* 原型期
* 低风险氛围台词
* 沙盒类涌现叙事
* 长尾状态解释
* 开发语义标签体系

但成熟系统中，核心权限、事实、状态和行动规则仍应程序化。

推荐演进路径：

```text
早期：
LLM 预处理 80%
程序化校验 20%

中期：
高频规则逐渐程序化
LLM 处理复杂组合和长尾情况

成熟期：
程序化语义层 80%
LLM 预处理只处理低风险模糊语境
```

---

## 8. 创作者接口设计

不建议把原始 prompt 编辑器作为主要创作入口。

推荐提供结构化创作接口。

### 8.1 角色配置

```json
{
  "name": "Elaine",
  "voice": {
    "style": "restrained, sharp, short sentences",
    "humor": "dry",
    "formality": "medium"
  },
  "core_desires": [
    "protect younger brother",
    "avoid public exposure"
  ],
  "core_fears": [
    "being discovered",
    "losing control of the situation"
  ],
  "social_tendencies": {
    "trust_gain": "slow",
    "anger_threshold": "medium",
    "confession_threshold": "high"
  }
}
```

### 8.2 场景配置

```json
{
  "scene_goal": "make the player suspect a hidden conspiracy",
  "tension": "medium_high",
  "allowed_reveals": [
    "someone is lying",
    "the docks are unsafe"
  ],
  "forbidden_reveals": [
    "the mayor is the mastermind"
  ],
  "preferred_speech_acts": [
    "evade",
    "warn",
    "partial_reveal"
  ]
}
```

### 8.3 叙事调音台

创作者可以调整：

* 当前章节主题
* 场景紧张度
* 允许揭露的信息
* 禁止揭露的信息
* 喜剧 / 严肃比例
* NPC 情绪表达强度
* 关系推进速度
* 秘密暴露速度
* 对话密度
* 台词长度

但不应直接修改：

* 权限过滤
* 状态事务
* 行动校验
* 核心系统 prompt
* 记忆写入规则

## 9. 调试与可观测性

动态 LLM NPC 系统必须具备调试工具。

每一句台词都应能追踪：

```text
为什么这个 NPC 说了这句话？
它依据了哪些事实？
它使用了哪些记忆？
它的 speech_act 是什么？
它是否引用了允许信息？
它是否触发了账本更新？
它是否改变了关系？
它是否被校验器修改或重试？
```

推荐提供调试面板：

```text
[Dialogue Debug]
NPC: npc_1024
Speech Act: bitter_complaint
Primary Emotion: resentment
Narrative Process: trust_erosion
Allowed Topics: unsafe work, exhaustion
Forbidden Topics: rebellion, leaving group
Knowledge Source: witnessed event_7781, memory_912
Validator Result: passed
Ledger Update: resentment +2
```

这对于开发、测试、创作者调参都非常关键。

---

## 10. 测试策略

应建立自动化测试集，而不是只靠人工试玩。

### 10.1 权限测试

验证 NPC 不会说出它不知道的事实。

```text
给 NPC 输入不含 hidden_fact 的知识包
期待输出不包含 hidden_fact 或其明显暗示
```

### 10.2 事实一致性测试

验证 LLM 不会创造不存在的事件、地点、人物、物品。

### 10.3 话语行动测试

验证指定 `speech_act = evade` 时，输出不会变成直接坦白。

### 10.4 强度测试

验证低强度抱怨不会升级为叛逃、威胁或暴力声明。

### 10.5 关系账本测试

验证相同事件组合能稳定产生相近关系变化。

### 10.6 回放测试

保存完整输入包：

```text
game_snapshot
knowledge_packet
semantic_packet
speech_act_plan
prompt
LLM_output
validator_result
ledger_update
```

之后可以回放、比较和回归测试。

## 11. 常见失败模式

### 11.1 上下文堆叠

症状：

* prompt 越来越长
* 信息越来越多
* 但台词并没有更稳定
* NPC 反而更容易跑题

解决：

* 不要继续加信息
* 改为增加语义编译和权限分层

### 11.2 角色全知化

症状：

* NPC 总像知道系统真相
* 秘密被过早暗示
* 角色反应过度精准

解决：

* 在 prompt 前做知识过滤
* 不让角色层看到 hidden facts

### 11.3 情绪漂移

症状：

* 同一 NPC 情绪忽冷忽热
* 关系缺少连续性
* 前一轮愤怒，后一轮突然友好

解决：

* 引入叙事过程和关系账本
* 情绪变化需要依据事件和阈值

### 11.4 台词漂亮但无功能

症状：

* 台词文学性不错
* 但不推进关系、信息或局面

解决：

* 先选 speech_act
* 再生成文本

### 11.5 LLM 改写游戏状态

症状：

* NPC 说自己给了玩家物品，但系统没有物品变更
* NPC 承诺加入阵营，但规则不允许
* NPC 说任务完成，但任务状态未完成

解决：

* 设计 Action Gateway
* 区分“语言表达”和“状态事务”

## 12. 推荐实施路线

### 阶段 1：最小可用原型

目标：

* 证明语义包比直接 prompt 更稳定

实现：

```text
读取 NPC 状态
手写简单语义编译规则
生成 speech_act
调用 LLM 写台词
显示输出
```

不做复杂记忆，不做 action。

---

### 阶段 2：引入知识过滤和权限层

目标：

* 避免角色全知
* 避免隐藏信息泄露

实现：

```text
系统事实层
角色知识层
权限标记
allowed / forbidden topic
```

---

### 阶段 3：引入叙事账本

目标：

* 让台词产生长期后果
* 让 NPC 关系和态度具备连续性

实现：

```text
关系变化
未完成冲突
承诺
秘密暴露进度
情绪过程
```

---

### 阶段 4：引入话语行动系统

目标：

* 让每句台词具备功能

实现：

```text
speech_act enum
speech_act selection rules
speech_act validator
```

---

### 阶段 5：引入行动网关

目标：

* 允许对话安全影响游戏状态

实现：

```text
action intent detection
programmatic validation
player confirmation
transaction commit
```

---

### 阶段 6：创作者工具与调试面板

目标：

* 让非程序创作者可控地调整体验
* 避免他们直接修改底层 prompt

实现：

```text
角色编辑器
场景目标编辑器
叙事调音台
ledger viewer
dialogue replay
```

---

## 13. 总结

动态游戏中的 LLM NPC 对话系统，不应该被设计成“动态 prompt 生成器”。

正确的核心不是：

```text
让 LLM 看到更多信息
```

而是：

```text
让系统在 LLM 开口之前，已经知道这句话为什么被说、能说到什么程度、说完会改变什么。
```

推荐架构是：

```text
底层游戏状态
  ↓
程序化语义编译
  ↓
主体知识过滤
  ↓
叙事过程识别
  ↓
话语行动规划
  ↓
权限与揭露控制
  ↓
LLM 台词渲染
  ↓
校验与事务处理
  ↓
叙事账本更新
```

一句话概括：

> LLM 是演员，不是导演；
> prompt 是表达接口，不是系统架构；
> 真正的核心是游戏状态到叙事语义的编译器。
